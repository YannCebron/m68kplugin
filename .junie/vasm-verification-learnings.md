# vasm Verification Learnings

This document records the lessons learned from verifying the m68kplugin against vasm.

## Test Design

### Reserved Words vs Symbolic Addresses

When testing whether vasm accepts a specific operand type, using a reserved word (like `sfc`) is insufficient. Vasm treats unrecognized operands as symbolic addresses.

**Example:** `tbls.w sfc,d0` assembles successfully. The test shows vasm accepts the instruction. But vasm treats `sfc` as a symbolic address, not as a control register. Any undefined symbol works the same way.

**Correct test method:** Test with the actual operand, an unknown symbol, and the equivalent address literal. Compare the generated bytes to confirm they are identical.

### Exit Code Interpretation

Exit code 0 means acceptance. Exit code 1 means rejection. Always check the actual exit code and output before drawing conclusions.

**Example:** A previous test showed `tst #0` assembled with exit code 0. The conclusion incorrectly stated "vasm rejects TST #Imm". The evidence showed acceptance.

## vasm Parsing Order

vasm parses operands in this order:

1. Immediate values (`#`)
2. Register names (Dn, An, FPn)
3. Special registers (via `getspecreg`/`getctrlreg`) — only if the operand type expects them
4. Memory addressing modes
5. Any bare name becomes an expression (symbolic address)

## CT Operand Type

The CT operand type in vasm's `opcodes.h` accepts memory addressing modes (bits 2, 5, 6, 7, 8, 9, 10). It does NOT include a special "control register" bit.

Control registers use the SEA (Special Extension And Addressing) mechanism. Instructions without SEA support cannot use control registers directly.

**Example:** TBL* instructions use the CT operand type. The registry generator maps CT to memory addressing modes correctly. Testing `tbls.w sfc,d0` succeeds because vasm parses `sfc` as an absolute address, not as a control register.

## Registry Generator Reliability

The registry is generated from vasm's `opcodes.h` and maps operand types correctly. When the registry says an instruction accepts certain operand types, it reflects the actual opcode definitions.

## Directive Argument Handling

When a vasm directive appears to accept arguments, check whether the handler actually parses them. Some handlers ignore the remaining text on the line.

**Example:** `clrfo 0` and `clrso 0` assemble without errors. The test suggests vasm accepts arguments. But the handlers (`handle_clrfo` and `handle_rsreset`) call `number_expr(0)`, which creates a zero value without parsing any input. The handlers ignore whatever follows the directive name. Testing `clrfo garbage text here` also succeeds.

**Correct test method:** Check the handler function in vasm source code. If it calls `number_expr(0)` instead of `parse_expr` or similar, the argument is ignored. Check the vasm documentation to see if arguments are documented.

## Verification Procedure

When verifying whether vasm accepts a specific operand type for an instruction:

1. Test with the actual operand (e.g., `sfc`)
2. Test with an unknown symbol to check if it's treated as an address
3. Test with the equivalent address literal (e.g., `$1234`)
4. Compare the generated bytes to confirm they are identical
5. Check the opcode definition in `opcodes.h` for the operand type
6. Check the operand type's supported addressing modes in `cpu.c`
